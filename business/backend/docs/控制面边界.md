# Platform 控制面边界

## 唯一事实源

| 事实 | 所有者 |
|---|---|
| 模块不可变发布、活动版本、路由、导航、权限定义、Registry revision | Platform Registry |
| 平台设置 | Platform Settings |
| 控制面审计 | Platform Audit |
| 用户、组织、成员、角色、策略、grant、DataScope、权益、会话、授权 revision | Identity |
| Access Identity 与 Module Capability | Identity |

Platform 不缓存或计算用户有效授权，也不调用 Identity Directory 取得主体后自行签发令牌。Manifest 中的权限是定义，不是授予；Platform 只将活动定义以版本化快照发布给 Identity。

## 工作负载权限

| 调用方 | 传输 | 唯一允许能力 |
|---|---|---|
| Gateway | mTLS/SPIFFE gRPC | `platform.registry.routes.read` |
| Identity | mTLS/SPIFFE gRPC | `platform.registry.active-capabilities.read` |
| Gateway | workload bearer HTTP | `registry.routes.read` |
| Release CI | workload bearer HTTP | `registry.release.write`、`registry.activation.write` |

未声明方法、未知 SPIFFE、错误证书、权限交叉或缺失 revision 一律 fail closed。健康检查只证明进程传输存活，不授予业务方法权限。

## 活动快照不变量

- 只发布 `active[moduleId]` 指向的不可变 release。
- 每个 module 都包含 release version、digest、backend、完整权限与贡献契约。
- snapshot revision 与生成内容来自同一 Registry state read。
- 返回对象是深拷贝，调用方修改不能污染 Registry 聚合。
- 激活或停用成功后 revision 单调增加；相同版本重复激活是无副作用幂等操作。
- 权限所有权冲突、路由冲突、导航组冲突时，active/revision/目录/审计均不变化。

## 授权迁移

历史授权迁移是离线两阶段交接，不是运行时兼容路径：

1. `authorizationexport` 在 MySQL advisory lock 下发现并锁定实际存在的历史表，将所有已知表的 `present` 状态和规范行写入不可变 ledger。
2. Identity 在自己的事务中导入 IAM 子集；Subscription 在自己的事务中导入 entitlement 子集，二者都验证 exact export digest/rowCount 并签发 receipt。
3. Platform 验证并持久化两份回执。Subscription 回执还必须声明目标导入行数与目标投影摘要；两份回执必须绑定同一 import ID 和 export。
4. 只有两份证据都成功后才执行幂等 drop；中断后使用完全相同 receipt 重试收敛。

任何不同 receipt、缺少历史表、读表错误、签名或目标不匹配都拒绝 finalize。命令与回执字段见 [授权交接.md](./授权交接.md)。
